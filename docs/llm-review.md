# LLM-анализ merge request

## Поток данных

```text
git diff base...head ─┐
описание MR и критерии ┼─► scripts/llm/context.mjs ─► модель (structured output) ─► guard.mjs ─► review.md / review.json
JUnit, lcov, тесты ────┘                                                                         └► комментарий в MR
```

| Вход | Источник |
|---|---|
| Diff | `git diff $CI_MERGE_REQUEST_DIFF_BASE_SHA...HEAD`. Свыше `RG_LLM_MAX_DIFF_CHARS` (400 000 символов) diff обрезается по файлам, пропущенные файлы перечисляются в запросе и в отчёте |
| Описание и критерии | GitLab API при заданном `RG_GITLAB_TOKEN`, иначе `CI_MERGE_REQUEST_DESCRIPTION`, которую GitLab может усекать. Критерии берутся из раздела «Критерии приёмки» или «Acceptance criteria» и нумеруются AC-1, AC-2… |
| Существующие тесты | Node-тесты (`test('…')`), Python-тесты (`def test_…`), kind-сценарии, Compose-регрессия из `release-rules.json` |
| Результаты | JUnit из `artifacts/junit/*.xml`, `artifacts/junit-scenarios.xml`, `artifacts/junit-regression.xml` |
| Покрытие | `artifacts/coverage/lcov.info`, доля покрытых добавленных строк по файлам |

Модель — `claude-opus-5-5` (переопределяется `RG_LLM_MODEL`) с adaptive thinking, `effort: high` и JSON-схемой ответа (`scripts/llm/schema.mjs`). Включён серверный fallback (`fallbacks: "default"`): если модель отклонит запрос по правилам безопасности, API повторит его на рекомендованной резервной модели. Модель, сформировавшая ответ, указывается в отчёте.

## Правила guard

| Ситуация | Итоговый статус критерия |
|---|---|
| Указан тест, он есть в репозитории и прошёл в этом pipeline | статус модели сохраняется |
| Тест существует, но его результата нет в отчётах | «не подтверждено» |
| Тест не найден или падает | «не покрыто» |
| Модель не оценила критерий | «не покрыто» |
| Модель придумала идентификатор критерия | запись отброшена |

Каждое такое изменение попадает в раздел «Исправления автоматической проверки». Файлы в предложениях помечаются как изменённые, существующие или новые.

## Настройка в GitLab

| Переменная | Назначение |
|---|---|
| `RG_LLM_REVIEW=true` | Включает job `llm-review` в MR-pipeline |
| `ANTHROPIC_API_KEY` | Masked, protected по необходимости |
| `RG_GITLAB_TOKEN` | Project access token с ролью Reporter и scope `api`. Нужен только для комментария и полного описания MR |
| `RG_LLM_LANGUAGE=en` | Отчёт на английском (по умолчанию русский) |

Содержимое MR отправляется во внешний API, поэтому включайте анализ только для проектов, где это допустимо.

## Проверка на демонстрационных PR

`examples/pr-review/<кейс>/` содержит:

- **Входы:** `description.md` (задача и критерии), `diff.patch` (правка реальных файлов репозитория), `junit.xml` и `lcov.info` (результаты pipeline для кейса).
- **Ожидания:** `expected.json` — какие риски должны быть найдены и какие критерии нельзя считать покрытыми.
- **Фикстура для guard:** `guard-fixture.json` — синтетический, вручную написанный ответ с заведомо ложными заявлениями о покрытии. Это не запись реального ответа модели.

```sh
node scripts/llm/eval.mjs          # guard исправляет ложные заявления; без модели, входит в unit-тесты и job unit
node scripts/llm/eval.mjs --live   # реальная модель на всех кейсах; job llm-eval-live, запускается вручную
```

В режиме `--live` для каждого кейса проверяются три условия:

- найдены ожидаемые риски (регулярные выражения из `expected.json`);
- критерии из `mustNotBeCovered` не помечены покрытыми;
- каждое оставшееся заявление о покрытии подтверждено пройденным тестом.

Отчёты сохраняются в `artifacts/llm-eval/`.
