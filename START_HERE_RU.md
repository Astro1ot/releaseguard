# ReleaseGuard — с чего начать

Это готовая первая версия проекта для DevOps-портфолио: небольшое приложение на NestJS и инфраструктура для проверяемых релизов и учебных инцидентов.

## Запуск без команд

Запустите Docker Desktop, затем дважды нажмите **Start-Lab.cmd** в папке проекта. Откроется панель http://127.0.0.1:8877 с кнопками запуска и проверок. Нажмите «Запустить / обновить», затем проходите сценарии по порядку. Панель показывает реальный результат каждого теста. Для Kubernetes доступны отдельные кнопки подготовки кластера и проверки отката.

Инструкция также сохранена на рабочем столе в файле **ReleaseGuard-инструкция.html**. Для остановки нажмите «Остановить стенд» в панели: данные PostgreSQL сохраняются.

## Посмотреть приложение

Из корня проекта, с Node.js 22+ и npm:

```sh
npm ci
npm run build
npm run demo
```

Откройте http://127.0.0.1:3000. Кнопка **Create test order** создаёт синтетический заказ. Демо явно работает в памяти: это проверка приложения и интерфейса, без настоящих PostgreSQL, Redis и Kafka.

Если `npm` не найден, нужен обычный дистрибутив Node.js с npm. В среде, где проект был создан, использовался отдельный локальный npm; он намеренно не включён в публикуемый исходный код.

## Запустить полный стенд

Нужен запущенный Docker Desktop в режиме Linux containers или Docker Engine с Compose v2. Сначала остановите демо, чтобы освободить порт 3000.

```sh
python cli/rg.py init-env
docker compose up -d --build --wait --wait-timeout 240
python scripts/integration.py
```

Страница через Nginx: http://127.0.0.1:8080. Grafana: http://127.0.0.1:3001, логин `admin`, пароль из созданного `.env`.

## Что показывать на собеседовании

1. Отличие готовности пода от работающего пользовательского сценария.
2. Точную предыдущую ревизию и проверку восстановления после отката.
3. Поведение клиента Redis при отказе и защиту от одновременных промахов кэша.
4. Атомарную запись заказа и outbox, обработку дубликатов событий.
5. Быстрый отказ DDL по `lock_timeout`, совместимость миграций с предыдущей версией приложения.

Полный сценарий: [docs/demo-script.md](docs/demo-script.md). Архитектура и ограничения: [docs/architecture.md](docs/architecture.md).

## Опубликовать

В папке уже инициализирован локальный Git-репозиторий с веткой `main`, без коммита и remote. Создайте пустой GitHub-репозиторий в своём аккаунте и следуйте [docs/publishing.md](docs/publishing.md).

Опубликуйте исходники, дождитесь CI, запустите ручной Kubernetes rehearsal и добавьте реальные результаты к описанию проекта. Не включайте `.env`, `.secrets/`, `node_modules/` и приватные логи. Эти пути уже исключены в `.gitignore`.

Формулировка для резюме после публикации репозитория:

> Разработал воспроизводимый DevOps-стенд на Kubernetes/Helm: бизнес-проверка релизов и верифицированный откат, PostgreSQL outbox и идемпотентная обработка Kafka, деградация Redis с ограничением нагрузки, Prometheus/Grafana и сценарии отказа. Код, инструкции и результаты испытаний опубликованы в репозитории.

Проверки относятся к локальному учебному стенду. Они не означают опыт эксплуатации коммерческого продакшена; на собеседовании показывайте конкретные сценарии и измерения.
